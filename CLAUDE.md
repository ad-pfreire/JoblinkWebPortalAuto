## What this is

Playwright QA suite for the Job Link web portal (Fieldpiece pre-staging: `https://joblink-portal.prestg.fieldpiece.com`). Runs against the **real pre-staging backend — no mocks**. See `README.md` for the full portal coverage map (what's automated vs. not) — keep that map updated whenever coverage changes.

## Hard safety rules (never break these)

- **The account behind `TEST_USERNAME`/`TEST_LOGIN_PASSWORD` in `.env`** (the maintainer's is `pfautomation`, email `paul.freire+automation@crifa.com`, but this is configurable per environment — see "Portability" below) is the **shared seed account** every spec file logs in with. Its real password must **never** actually be changed, and it must **never** actually be deleted, by any test.
- Tests that need to register, verify-by-email, change a password for real, or delete an account for real must use a **fresh, disposable, run-unique account** (`generateUniqueEmailAlias()` / `registerNewAccount()` / `completeProfile()` in `tests/utils/account.ts`) — never the seed account.
- Any test that mutates one of the seed account's persistent fields (First/Last Name, Phone) **must restore it before the test ends**, and must verify the restore actually persisted via a real reload/response check — not just a success-toast check (see "Known gotcha" below).
- `.env` holds real credentials and is gitignored — never commit it, never print its contents in a way that gets committed.

## Known gotcha: don't trust the toast for a second save in the same test

If a test does two real saves close together (dirty a field → save → restore → save again), the first save's success toast can still be on screen when the second one fires. Asserting on toast **text** alone can pass without the second save having actually completed, and an immediate `page.goto()` reload can race the still-in-flight request. Fix: wait for the real network response (see `saveAndWaitForSuccess()` in `tests/profile-settings.spec.ts`), not just toast visibility, whenever a cleanup save follows another real save in the same test.

## Known gotcha: an uploaded image's src/URL can keep changing for ~15-25s after a successful upload

On both Profile Photo and Company Logo Upload, the success toast and the immediate DOM update happen right away, but the saved file's URL is **not final yet** — the backend appears to asynchronously post-process the upload (likely generating an optimized/resized variant), and can swap the displayed `src` to a different URL more than once over the next ~15-25s, even with zero navigation. It does settle permanently after that window. Any test asserting an upload's "final" URL (e.g. across a reload) must poll for the src to stop changing first — capturing it immediately after the toast/response and comparing later will intermittently fail. See `waitForStableImageSrc()` in `tests/logo-upload.spec.ts` (polls for 3 consecutive matching reads, 1s apart, over up to 25s — 2 consecutive reads and/or a 10s budget were both empirically not long enough) and remember to `test.slow()` any test that calls it, since the wait alone can exceed the default 30s test timeout.

## Known gotcha: reading a POST response body can race the app's own client-side navigation

`await response.text()` after `page.waitForResponse(...)` can intermittently throw "Response body is not available for a response that was navigated away from" — even when read inside the very same `.then()` as the response resolving, with no explicit `page.goto()` in between. Seen on Logo Upload's WEBP-rejection case, where the app appears to trigger some internal client-side router activity shortly after that particular response resolves, discarding the buffered body before `.text()` can read it. Fix: intercept the request with `page.route()`, call `route.fetch()` yourself, read `.text()` on that response deterministically, then `route.fulfill({ response })` so the app still gets the real response and behaves normally — see the `page.route('**/company', ...)` block in test 3.4 of `tests/logo-upload.spec.ts`. Confirmed via 3 back-to-back full test-file runs that this fully eliminates the race (the plain `waitForResponse().then(r => r.text())` approach still failed intermittently even reading the body "eagerly").

## Known gotcha: `fill('')` and real keystrokes can trigger different validation timing

A form library's validation can behave differently for a raw `locator.fill('')` (value replaced in one DOM operation) versus a real user clearing a field character-by-character with Backspace. Confirmed on Company Details: an earlier live-exploration draft concluded that clearing a required field silently suppressed "The field is required" - re-verified with BOTH techniques and found `fill('')` and real Backspace keystrokes actually behaved the same in that specific case (the original finding was wrong for other reasons), but the discrepancy-hunting surfaced this as a real, general risk worth guarding against. When a test's whole point is validation-triggering (not just getting a field into some end value), prefer real keystrokes (`page.keyboard.press('Backspace')` in a loop, or `pressSequentially()`) over `fill()` - see `clearFieldWithBackspace()` in `tests/company-details.spec.ts`.

## Known gotcha: `getByRole('alert')` can match Next.js's own route-announcer, not just app messages

Next.js injects an always-present, empty, visually-hidden `<div role="alert" id="__next-route-announcer__">` into every page for screen-reader route-change announcements. A test asserting "no error alert appeared" via `getByRole('alert')).toHaveCount(0)` will fail against this element even when the app itself shows nothing - it's not a bug, just an unrelated a11y element that happens to share the `alert` role. Assert the alert's **text is empty** (`toHaveText('')`) instead of asserting zero count. See test 3.4 in `tests/company-details.spec.ts`.

## Known gotcha: `innerText` vs `textContent` can fabricate a false "missing space" bug

A read-only summary field rendering two values separated by a real `<br>` (e.g. Company Details' "Location": address on one line, city/state/zip on the next) is genuinely two clean lines to a real user. Reading it via `textContent` (which ignores `<br>`) or via an accessibility-tree name computation can make it look like the two values ran together with no separator ("...BroadwaySanta..."). Always verify a suspected string-concatenation bug with `locator.innerText()` (respects real rendering) and/or direct DOM inspection before reporting it as a defect - this exact false positive was caught and corrected in `specs/company-details-test-plan.md` section 4.3 after initially being reported as a real bug.

## Known gotcha: a live third-party API call can cascade-skip an entire `mode: 'serial'` file

Company Details' Address field uses a real (unmocked) Google Places Autocomplete API, which occasionally doesn't respond with suggestions inside a generous timeout - genuine external flakiness, not a bug. In `test.describe.configure({ mode: 'serial' })`, one failed test skips every remaining test in that file as "did not run", so a single flaky external call can silently zero out an entire spec file's results. Fix: add `retries: N` to the same `describe.configure({ mode: 'serial', retries: 2 })` call for any file with a real external dependency baked into a serial sequence - Playwright re-runs the failed test (and, in serial mode, everything from that point onward) rather than abandoning the rest of the file. Only safe when the flaky test doesn't leave residual mutated state on failure (Company Details' Address test never saves, only reloads to discard) - see `tests/company-details.spec.ts`.

## Known gotcha: `test.beforeAll(async ({ browser }) => ...)` + `browser.newPage()` silently drops the project's context options - can break real email delivery

A spec file that registers ONE disposable account ONCE in `test.beforeAll` (the account-isolation pattern documented below, first used in `tests/payments.spec.ts`) needs its own `Page`, since `beforeAll` has no `page` fixture. Calling `browser.newPage()` directly creates that page in a **bare default context** - it does NOT inherit this project's configured `devices['Desktop Chrome']` context options (viewport, and critically, user agent) the way the normal per-test `page` fixture does. A bare Chromium context's default user agent contains `HeadlessChrome`, and live-verified while writing `tests/payments.spec.ts`: three consecutive real registrations done this way never received their verification email within a 240s budget, while the exact same registration flow run via the standard `page` fixture (`account-registration.spec.ts`'s own real-email test) delivered in ~35s every time, run back-to-back with the failures. The account itself was created successfully either time (confirmed via the app's own "Email Verification" pending screen) - only the email delivery was affected, consistent with some anti-abuse/WAF layer in front of the real pre-staging registration endpoint treating a headless-looking signup differently. Fix: `await browser.newContext({ ...devices['Desktop Chrome'] })` (import `devices` from `@playwright/test`) instead of `browser.newPage()`, then `context.newPage()` and `context.close()` instead of `page.close()`.

## Known gotcha: Stripe Elements (iframe) fields need real keystrokes, not `fill()`, to register as "complete"

Confirmed on Payments' Stripe-hosted Billing Address and Card iframes (Stripe.js AddressElement/CardElement): `locator.fill('4242424242424242')` sets the visible value correctly, but Stripe's own internal per-field "complete" tracking — which the app's "Update Payment Method" button's enabled state depends on — does not update from a `fill()`. The button stayed disabled with a textually-valid, `fill()`-populated card even with the required "Save payment details" checkbox checked; retyping the identical value with `pressSequentially()` (`slowly: true`) fixed it immediately. Same root cause as the `fill('')` vs. real-keystrokes gotcha above, called out separately because it's specific to Stripe's iframe-based Elements — use real keystrokes for any Stripe Elements field in this app. Separately, the "Save payment details for future purchases" checkbox itself was observed to occasionally need a second click to actually register as checked (a Playwright click can report success while the checkbox's real `checked` state and the button's `disabled` state don't reflect it) — verify the checkbox's actual DOM state after clicking rather than assuming a single click always lands.

## Known gotcha: Stripe's own iframes for the SAME element can silently multiply and even swap mid-test — a plain `page.frameLocator('iframe[title="..."]')` is not safe long-term

Extensively live-verified while writing `tests/payments.spec.ts`'s Card Form Validation suite - this is a genuinely deep rabbit hole worth understanding fully before touching any Stripe Elements iframe in this app again:

- Both the Billing Address (`title="Secure address input frame"`) and Card (`title="Secure payment input frame"`) iframes can have MORE THAN ONE iframe sharing that exact same `title` on the page at once, for at least two independent, non-deterministic reasons: (1) Stripe occasionally mounts a second, hidden (`aria-hidden="true"`) accessory iframe (e.g. `elements-inner-autocomplete-suggestions-*.html`) carrying the identical title text; (2) separately, Stripe's own "Link" (saved-payment/WebAuthn autofill) component mounts its own accessory iframe ALSO carrying the identical title and ALSO not `aria-hidden`. Neither `:not([aria-hidden="true"])` alone nor a further `allow*="publickey-credentials-get"` attribute exclusion (Link's iframe has this WebAuthn-specific permission, the real input frame doesn't) turned out to be a *stable* way to exclude the decoy — in one run the "real" frame itself carried that same permission, breaking the exclusion.
- Worse: the genuinely real, interactive iframe for a given Element can get SWAPPED for an entirely new iframe instance (a new `name` attribute) partway through a single test's interactions with it — not just have a decoy mounted alongside it. A `paymentFrame`/`addressFrame` reference captured once at the top of a test and reused for several sequential field fills is a real, reproducible flakiness source: an action into it can hang for a real 30-90s (not fail fast) once the frame it's pointing at goes stale.
- The fix that actually held up under repeated re-verification: resolve by CONTENT, not by attribute or DOM order. Query every `iframe[title="..."]` candidate, and for each, check (inside its `contentFrame()`) whether it actually contains the field you expect (e.g. `getByRole('textbox', { name: 'Card number' })`); the first candidate that does is the real one. Read that candidate's own `name` attribute and build the final `FrameLocator` from `iframe[name="<that value>"]`, NOT from the ambiguous title selector — `name` is unpredictable in *value* across page loads but stable for one specific mounted iframe instance for the rest of that page's life, unlike a title-based or `.nth()`-based selector which Playwright re-evaluates live on every subsequent action. See `resolveStripeFrameByContent()` in `tests/payments.spec.ts`.
- Because a mid-test swap can happen at any point, don't capture `paymentFrame`/`addressFrame` once and reuse it across multiple sequential field fills either — re-resolve fresh (call the resolver again) before each individual field interaction in any test that does more than one or two actions against the same Element. This is more expensive but was the only thing that made a multi-step test (several fields + several assertions) reliable across repeated real runs.
- A page-load timing corollary: these iframes mount asynchronously after `page.goto()` resolves, so any resolver needs to POLL (not check once) — an immediate zero-candidate count right after navigation just means the iframe hasn't mounted yet, not that it never will.

## Known gotcha: `page.getByRole('alert', { name: '...', exact: true })` can report "not found" even while the exact text is already visible in the DOM

Live-verified via direct diagnostic logging on Payments (submitting a form with a required Stripe AddressElement field left blank): `page.evaluate(() => document.querySelectorAll('[role="alert"]'))` found the expected error text (e.g. `'Please provide your full name.'`) present, in duplicate, in the top-level document the SAME instant that `expect(page.getByRole('alert', { name: '...', exact: true })).toBeVisible()` was timing out with "element(s) not found". Root cause not fully isolated (Playwright's accessible-name computation for these MUI `Alert` regions not lining up with their live textContent in this instant - possibly an ARIA live-region timing quirk, not something this suite controls), but the practical fix is straightforward and more robust anyway: assert on visible TEXT (`page.getByText('...', { exact: true }).first()`, `.first()` because the same alert can genuinely render twice - same general "hidden duplicate" pattern already documented elsewhere in this app) rather than role+accessible-name matching, whenever asserting that a *specific* alert message appeared. This is a distinct issue from - but the same general family as - the already-documented Next.js route-announcer `getByRole('alert')` gotcha above; between the two, prefer text-based assertions over role-based ones for this app's alerts generally.

## Known gotcha: Stripe's 3D Secure test-challenge 'Complete'/'Fail' buttons render before their own click handler is wired up

Live-verified on Payments test 5.4 (3D Secure flow): the challenge iframe's 'Complete' button becomes DOM-visible (passes Playwright's actionability checks) before the challenge page's own JS (`challenge.js`, gated behind a separately-loaded `trusted-types-checker` script) has finished loading and attaching its click handler. A `click()` fired immediately after the button's visibility assertion resolves lands cleanly with no Playwright error, but is a silent no-op - trace network timing showed the click landing ~1.5s before `trusted-types-checker-*.js` even finished its network request, with ZERO further network activity of any kind afterward (no `3ds2/authenticate` follow-up, no app-side confirmation call), all the way through a 45s timeout waiting for the post-3DS redirect to `/company`. Reproduced 2/2 times once the real email pipeline allowed the test to actually run (see the `beforeAll`/real-email gotcha above - the other apparent failures in the same session were that separate, well-known infra flakiness, not this bug). Fix: an explicit `page.waitForTimeout(2_000)` after the challenge heading/buttons are confirmed visible, before clicking 'Complete' - see test 5.4 in `tests/payments.spec.ts`. **Caveat added 2026-08-26**: a *different*, superficially similar-looking CI-only Checkout failure (see the GPU/hCaptcha gotcha below) was initially misdiagnosed as this same mechanism, and two separate timing-based fixes for it (a blind pause, then a deterministic network-response wait) both failed to help, because the real cause there turned out to be something else entirely. This 3D Secure finding itself was never actually re-verified against that possibility - if this exact gotcha ever resurfaces despite the settle-pause fix, download a real trace and check the button's own post-click DOM state (does it show "Processing"/some busy state, meaning the click DID land?) and the Stripe API's own record of that flow before assuming it's the same click-timing issue again.

## Known gotcha: `subscription.spec.ts` test 4.2 (real Stripe Checkout purchase) can hang forever in CI only - two real, distinct causes found, one fixed, one accepted as an environment limit

Live-verified 2026-08-26: failed identically 5/5 real CI runs, never once locally. Two blind/semi-blind timing fixes were tried first (a 2s pause, then a deterministic `page.waitForResponse()` wait for a Stripe script) and both failed - the first real clue this wasn't a click-timing race. Downloaded failing runs' actual traces and cross-referenced Stripe's own API record for the exact Checkout Sessions involved to find what was really happening: the trace's post-click DOM snapshot shows the Subscribe button's own text changing to "Processing" (the click DOES land and fire the handler), but `stripe.com/v1/checkout/sessions/<id>` (queried directly via the Stripe API with a restricted key) showed `status: "open"` and `payment_intent: null` - the payment submission never reaches Stripe's servers at all, and the network log goes completely silent after the click (not slow - zero further requests of any kind, not even Stripe's own periodic analytics beacons) for the rest of the 45s timeout.

**Cause #1, found and fixed**: on the first several failing runs, the trace's captured browser console showed the hCaptcha invisible-verification iframe (which Checkout's submit flow needs a token from before it will submit) logging `"[.WebGL-...] GL Driver Message (OpenGL, Performance, GL_CLOSE_PATH_NV, High): GPU stall due to ReadPixels"` a few seconds in. GitHub Actions' shared runner has no real GPU, and hCaptcha's invisible check apparently depends on WebGL rendering that never completes cleanly there. **Fix**: `subscription.spec.ts`'s own top-level (module-scope, not inside `test.describe`) `test.use({ launchOptions: { args: [...] } })` now passes `--use-gl=angle`, `--use-angle=swiftshader`, `--enable-unsafe-swiftshader` to Chromium when `process.env.CI` is set, forcing it onto its own supported software-rendering path. Confirmed via a downloaded trace that this specific GPU stall message is gone on subsequent runs.

**Scoping this fix correctly mattered more than it looked like it should.** The first version put the same `launchOptions` at the `chromium` *project* level in `playwright.config.ts` instead - fixed test 4.2, but broke two unrelated, previously rock-solid timing-sensitive tests in `profile-settings.spec.ts` (a rapid-double-click dedup test and a rapid-keystroke type-ahead test) on the very next CI run, failing the blocking "core" step for the first time in over a week of clean runs. CI forces `workers: 1` - one shared Chromium process for the whole suite there - so a project-level `launchOptions` change touches every test, and software rendering being measurably slower at compositing was apparently enough to shift timing in those two already-tight tests. Moving the same `launchOptions` into `test.use()` scoped to just this file fixed it: Playwright launches a separate browser instance for a file whose resolved `launchOptions` differ from the rest of the suite's default. **General lesson for this project**: any fix touching `launchOptions` (or anything else that could resolve differently per file) belongs in the narrowest `test.use()` scope that covers the actual affected test(s) - never assume a project-level config change is "just for this one file," especially under CI's single-worker setup.

**Cause #2, found but NOT fixed - accepted as a known CI-environment limitation**: even after cause #1's fix confirmably eliminated the GPU stall message, test 4.2 kept failing in CI with the exact same outward symptom (click lands, total silence, 45s timeout). A newer trace showed hCaptcha's `getcaptcha` endpoint called a *second* time near the point where things go silent, plus Google Pay/Google Play buy-flow network activity not present in earlier traces - consistent with a second, independent verification step (possibly hCaptcha's actual bot-detection heuristics, now that the environment issue no longer masks it, or an express-checkout-related check) also not completing cleanly from GitHub Actions' shared-runner IP range. This is consistent with a genuinely hard, industry-wide problem - hCaptcha exists specifically to distinguish real users from automation, and pure Playwright automation from a well-known datacenter IP range is close to a worst case for that. **Decision (2026-08-26, discussed with the maintainer)**: stop chasing this specific failure mode further. Test 4.2 stays tagged `@real-email`, running in CI's non-blocking "known flaky" step (never the blocking "core" step) - it never fails locally, and the two real, fixable bugs found along the way (the IMAP reconnection issue and the GPU rendering issue) both got fixed and benefit the whole project regardless. If a future session wants to revisit this, start from Cause #2's own evidence above rather than re-diagnosing from scratch - and consider whether it's worth pursuing before spending real time on it, given its likely root cause is an anti-automation system working as intended.

**Confirmed 2026-08-28/29: this is not unique to `subscription.spec.ts`** - any file whose setup drives a real Stripe Checkout purchase can hit the identical symptom in CI's real-email step. Two back-to-back CI runs while validating unrelated changes to `teams-plan-gating.spec.ts` both failed its `beforeAll`'s own Checkout purchase (a `test.4.2`-style step, unrelated code, untouched by either change being validated) with the exact same signature - stuck on `checkout.stripe.com`, never redirecting, 45s timeout - and `account-deletion-billing.spec.ts` test 3.1's own Checkout purchase failed the same way in the same two runs. All three files are already correctly tagged `@real-email` and run in the non-blocking step, so this doesn't gate merges - but don't mistake a Checkout-purchase failure in a NEW file's CI-only real-email run for a new bug in that file's own code; check whether the failure point is the shared Checkout-purchase step itself before investigating further. The blocking "core" step is unaffected by any of this (Checkout purchases are never part of it) and passed cleanly in both runs.

## Known gotcha: a Stripe Elements iframe's sentinel field being present doesn't mean the REST of that same widget has finished mounting - and this can be invisible locally, only surfacing in CI

`resolveStripeFrameByContent()` (Payments' core Stripe-iframe resolver, see its own comment above) confirms a candidate iframe is real by checking for ONE sentinel field (e.g. 'Full name' for the Billing Address widget). Live-verified this is not sufficient on its own: the FIRST-ever GitHub Actions run of `payments.spec.ts` hung a full 90s on 'Address line 1' immediately after this exact resolver had just confirmed the same frame already contained 'Full name' - the rest of the AddressElement widget (Address line 1/City/Postal code) simply hadn't mounted yet, even though the sentinel field had. Never reproduced across ~20 full-file runs on a local dev machine, only on CI's slower/more resource-constrained shared runner - a genuinely environment-dependent timing gap, consistent with this app's general pattern of async Stripe-adjacent JS needing more settle time than a fast local machine ever exposes. **Don't assume a passing local run means CI will pass too for anything touching these iframes** - CI is measurably slower and can expose races a fast machine never hits. Fix: `billingAddressFrame()` now also explicitly waits for the Address line 1 field's own stable Stripe element id (`#billingAddress-addressLine1Input`, role-agnostic since its role switches between textbox/combobox by country - see the id-based fix below) to be `attached` before returning the frame, not just the sentinel field.

## Known gotcha: some Stripe Address fields only get an accessible name from an external `<label for="...">`, not a direct `aria-label` - and that association isn't always reliably attached yet when read

Live-verified via direct DOM inspection (`browser_run_code_unsafe` against a real live page, since cross-origin iframes block `page.evaluate` from the top frame): inside the Billing Address AddressElement iframe, 'Full name'/'Address line 1'/'Country or region' get their accessible name from label association that's present from first mount, but 'City'/'Postal code'/'Address line 2' do NOT carry a direct `aria-label` - their name comes purely from a separate `<label for="billingAddress-localityInput">` element. That `for`/`id` pairing is structurally valid on a plain fresh load (confirmed live), but a fast, type-free read/fill sequence can hit a reproducible race where `getByRole('textbox', { name: 'City' })` reports 'element(s) not found' - even after wrapping the whole resolve-then-read cycle in a 15s `toPass()` retry loop, which never once found it. **Originally believed confined to the one context Payments' Suite 6 exercises** (loading `/payments` when a payment method is ALREADY saved, so 'Current Payment Method' renders above the form - possibly triggering a widget reflow Suite 5's fresh-form-only loads never hit) - **disproven 2026-08-24**, when a plain local run hit the identical race on a completely fresh-form load (Suite 4's own City fill, no saved payment method involved) - so this can surface on any load of the Address iframe, not just Suite 6's. The Card iframe's fields (Card number/Expiration date/Security code) are NOT affected - they carry a direct `aria-label` attribute, confirmed via the same DOM inspection. Fix: for the Address iframe's non-obviously-labeled fields specifically, read/fill by the field's raw Stripe-assigned element `id` (e.g. `#billingAddress-localityInput` for City, `#billingAddress-postalCodeInput` for Postal code - stable and semantically named, not per-session-random, confirmed via live inspection) instead of `getByRole(..., { name })`, sidestepping accessible-name computation entirely - applied to every City/Postal code read or fill throughout `tests/payments.spec.ts`, not just test 6.1's original assertions.

## Known gotcha: a `test.beforeEach` that re-logs in and navigates before EVERY test means later tests can't assume client-side UI state (an open dialog, a filled form) survives from the test before it

Backend-persisted state (a saved payment method, an active subscription) correctly carries over between two consecutive tests in a serial-mode file, because a fresh page load re-fetches it from the real server. Pure client-side React state - like a dialog left open at the end of one test - does NOT, because this file's own `test.beforeEach` (`loginAsDisposableAndGoToCompany`) runs before every single test, no exceptions, resetting to a fresh `/company` page each time. Payments test 6.7 originally assumed 6.6's 'Cancel Subscription' dialog was still open when it started (matching the original test plan's prose, never freshly live-verified per the generator's own admission) - live-verified via direct DOM inspection of a CI failure that 6.7 actually starts on a plain `/company` page with no dialog present at all. Fix: 6.7 now re-opens the dialog itself (navigate to `/payments`, click 'Delete Payment Method & Cancel Subscription' again - the account still has its payment method and active subscription at this point, since 6.6 only opened and inspected the dialog, never actually clicked 'Finish Cancellation') before interacting with it, rather than assuming state left by the previous test.

## Known gotcha: `test.skip(browserName !== 'chromium', ...)` inside `beforeEach` does NOT protect a file's `beforeAll` from also running on the other projects

The account-isolation pattern for files that register their own disposable account once in `beforeAll` (see "Account/company isolation" above, first used by `tests/payments.spec.ts`) needs its OWN `browserName` guard inside `beforeAll` itself - the `test.skip(browserName !== 'chromium', ...)` already present in this file's `beforeEach` only skips individual TESTS, it does nothing to gate `beforeAll`, which runs once per project regardless and BEFORE any test-level skip logic ever gets a chance to apply. Live-verified via a real GitHub Actions run (3-project matrix: chromium/firefox/webkit): without a matching guard inside `beforeAll` too, firefox and webkit were EACH independently registering a fresh disposable account and waiting up to 3 x 240s for a real verification email - for a file whose every single test then immediately skips on those two projects anyway. Three real accounts hitting the same real email pipeline back-to-back-to-back (one per project, potentially overlapping) is also exactly the kind of concurrent load this project has repeatedly seen degrade that pipeline's reliability. This was invisible locally (`--project=chromium` was always used explicitly there) and only surfaced running the full 3-project matrix in CI. Fix: add the identical `test.skip(browserName !== 'chromium', ...)` check as the very first line of `beforeAll` too (with `browserName` destructured from its fixtures alongside `browser`), not just in `beforeEach` - see `tests/payments.spec.ts`. Any future file following this same beforeAll-registers-once pattern needs this same double guard.

## Known gotcha: combining `to` with `since` in `tests/utils/email.ts`'s IMAP search can spuriously return zero results when `since` falls on "today"

Live-verified while writing `tests/teams.spec.ts`'s test 6.7: `ImapFlow.search({ to: toAddress, since })` against this Gmail account can return an empty result for a message that is genuinely already sitting in the mailbox, specifically when `since`'s calendar date equals "today". A `since` from any strictly earlier calendar day works correctly (and still correctly includes today's messages, since IMAP's SINCE means "on or after"). Reproduced 3 times in isolation, changing only `since`: `since: <yesterday>` found the message instantly; `since: <today, any time value>` returned `[]` even though the message's real internal date was hours after that `since` value — confirmed via a `to`-only re-query that this was never a delivery-speed issue, the message was already there the whole time.

This matters project-wide, not just for Teams: `getVerificationLink()`/`getPasswordResetCode()` always pass `since = registeredAt`/`since = <moment just before requesting the email>`, i.e. almost always "today" — so this bug is a real candidate for having caused at least some of the "email pipeline is slow" 240s timeouts this project has historically attributed purely to real pre-staging infra flakiness. **Fixed**: both functions now search by `to` alone, ignoring `since` entirely (the `sentAfter` parameter is kept in both signatures, marked `void sentAfter;`, to avoid a signature change rippling across every call site in `account-registration.spec.ts`/`forgot-password.spec.ts`/`profile-settings.spec.ts`/`payments.spec.ts`/`teams.spec.ts`). This is safe because every call site in this project always passes a freshly `generateUniqueEmailAlias()`d address that has never received mail before, so a `to`-only search can never collide with a stale message from an earlier run. The new `getInvitationLink()` helper (see next gotcha) uses this same safe `to`-only pattern from the start.

Important nuance: this fix does **not** eliminate all email-timing flakiness — real delivery delay under heavy mailbox load (this project has seen 50+ messages arrive in a 30-60 minute window during heavy same-day testing) is a separate, still-real phenomenon. Both things can be true at once: a genuine search bug AND genuine infra slowness were compounding each other. If a future session considers loosening this further (e.g. re-adding a `since` filter for a case where address reuse is possible, like a hypothetical future test that reuses one address across multiple `getPasswordResetCode()` calls), re-verify this exact boundary condition doesn't resurface.

## Known gotcha: holding one IMAP connection open across a whole polling loop can silently never see mail that arrives mid-poll

Live-verified 2026-08-25 while writing `tests/subscription.spec.ts`: all three `tests/utils/email.ts` functions (`getVerificationLink`, `getInvitationLink`, `getPasswordResetCode`) used to open a single `ImapFlow` connection and mailbox lock once, then loop `search()` calls against that same open connection/lock until the email showed up or the budget ran out. This can silently miss mail that arrives while that connection is held open — reproduced across 10+ consecutive real runs escalating the timeout budget from 240s to 480s to 900s, always still "timing out" even though a completely independent, freshly-connected IMAP check confirmed the email had been sitting in the mailbox the whole time (often within the first 30-60s). This is a distinct bug from the `to`+`since` search bug documented above — even a `to`-only search can miss mail if it's run repeatedly against one long-held connection/lock instead of a fresh one. **Fix**: all three functions now open a brand-new `ImapFlow` connection, connect, search, and logout, on **every single poll iteration**, instead of connecting once and looping `search()` inside one held-open session. Validated in isolation post-fix: an email that previously required 900s+ (or never) was found in ~15s. This is more expensive per-poll (a fresh TCP+TLS+auth handshake every iteration) but is the only version that reliably saw new mail — worth the cost given how much downstream flakiness the old behavior caused project-wide.

## Known gotcha: accepting a real team invitation is a multi-step flow with its own separate email — don't assume it mirrors registration

Live-verified end-to-end while writing `tests/teams.spec.ts`'s test 6.7 (the only place in this project this flow is exercised):

- The invitation email's subject is exactly **"New Invitation!"** — a completely different Mandrill/SES template from the "Job Link Registration Confirmation" verification email `getVerificationLink()` reads. Its link (`/invitation?token=<JWT>`) is embedded as **plain text inside a `<p><span>`**, not as a real `<a href>` button, and is **not** Mandrill-click-wrapped (unlike the verification link) — see `getInvitationLink()` in `tests/utils/email.ts` for the extraction pattern this required.
- Visiting the invitation link while logged out redirects to `/login?redirectUrl=<the invitation URL>` with the invitee's email **pre-filled** into "Username or Email", and the "Sign Up" link itself carries `?email=<invitee's email>` to pre-fill registration.
- **Completing registration does NOT auto-redirect back to the invitation** — the invitee has to manually revisit the original invitation link again after finishing registration + email verification + complete-profile. A real spec-file implementation needs to hold onto that link across the whole registration round-trip.
- Once logged in as the correct invitee, the invitation link shows a heading "You've been invited!" and body text "We found your invitation to `<inviter's full name>` Job Link team!", with 'Reject'/'Accept' buttons — the Accept button carries `data-testid="accept-btn"` (no accessible role/name of its own worth relying on).
- Visiting the SAME link while logged in as a **different** account shows "Invalid Invitation" — "This invitation link is associated with a different user. Please sign in with the correct account." — confirmed this is a real, distinct negative-path screen, not a generic error.
- Accepting makes the invitee a real, company-wide "Active" member (visible under `/teams/members`), but does **NOT** also add them to the specific team they were invited through — that needs its own separate "+ Add Members" action from that team's own detail page. Don't assume company membership and team membership are the same step.
- A test chaining this whole flow needs a generous explicit timeout, not `test.slow()`'s 3x multiplier: `test.slow()` still hit its own 90s wall live (twice, back to back) against two real chained email waits (`getInvitationLink()`'s up to 150s + `getVerificationLink()`'s up to 240s) plus UI steps. Use `test.setTimeout(480_000)` (or similarly generous) instead — see test 6.7 in `tests/teams.spec.ts`.

## Known gotcha: manually driving the MCP browser tools while a background subagent is also using them causes the two sessions to collide

Live-verified mid-session while writing `tests/teams.spec.ts`: calling `planner_setup_page`/`browser_*` tools directly (outside any subagent) WHILE a `playwright-test-generator`/`playwright-test-planner` subagent is running in the background and also using its own `browser_*` tools can result in both sessions sharing the same underlying browser instance — actions from one appear to interleave with or override the other's, producing confusing, seemingly-impossible page states (e.g. a manual `browser_navigate` to `/register` landing on a completely different page mid-login, logged into the shared seed account with an unrelated modal open, because a concurrently-running subagent's own exploration was actually what the tool was reporting back). Fix: never drive the MCP browser tools manually while a background subagent that also uses them is still running — wait for it to finish (or stop it) first.

## Known gotcha: `profile-settings.spec.ts`'s wrong-Current-Password tests can trip Cognito's own real account-level attempt-limit throttle on the shared seed account

Root cause found and fixed 2026-08-27 for the CI instability first noted in `handoff.md` on 2026-08-27 (`Change Password › "should show a generic error... for a wrong Current Password"` failing twice in a row in CI with the exact same symptom: `expect(locator).toBeVisible()` timing out on "An unexpected error occurred. Please try again later." never appearing). Root cause was **not** a timing race in the test — live-verified directly by scripting the same wrong-Current-Password submission against the real seed account several times in a short window (a handful of manual re-runs plus this file's own test suite, all within ~15 minutes): after enough real failed-password attempts pile up, Cognito's own `LimitExceededException` kicks in and the modal shows **"Attempt limit exceeded, please try after some time."** instead of the app's intended generic wrapper text. This is a real Cognito rate limit on the account itself, not a per-IP or per-worker thing, and it persists across separate process runs (including separate CI job runs) until Cognito's own cooldown window elapses.

This is a structural hazard, not a one-off: **every** run of this file submits at least one real wrong Current Password against the ONE shared seed account (two tests do — the generic-error test itself, and the rapid-double-click dedup test), and this project already runs CI repeatedly in a row when iterating on unrelated fixes (see "Portability" below on the CI concurrency queue) — so the seed account's failed-attempt count accumulates across runs far faster than a human would expect from any single test file in isolation. Cognito's rate-limit message is not itself a defect in the app (it's arguably reasonable, not-sensitive information to show a real user, unlike leaking "Incorrect username or password.") — it's an artifact of this suite's own shared-account model combined with frequent real re-runs.

**Fix**: `expectGenericPasswordChangeError()` (`tests/profile-settings.spec.ts`) waits for *either* banner, and calls `test.skip()` with a clear reason if the rate-limit banner is the one that actually appeared, instead of asserting only on the intended generic-error text and failing opaquely when the account is (harmlessly, temporarily) throttled. Both call sites in this file (the generic-error test and the rapid-double-click test) use this helper now. Any future test in this file that needs to submit a real wrong Current Password against the seed account should use the same helper rather than asserting on the generic-error text directly.

## Account/company isolation: not every new area needs to share the seed account

Live-verified 2026-08-17/18 while exploring Payments: every self-registered account gets its own fully isolated Company record. A fresh disposable account's `/company` page shows its own blank Company Details, its own "No Payment Method" / "No Payment History", and its own Subscription trial end date — all completely independent of the shared seed account's. This means the "must share the one seed account" constraint documented below for Company Details/Logo Upload/Profile Settings is **not a universal rule** — it applies there specifically because Email/Username are read-only fields sourced from the account itself, not because Company-level data is inherently shared across accounts.

For a new area where nothing forces use of the real seed account (Payments was the first confirmed case), prefer a **third pattern**, distinct from both existing ones:
- NOT the shared seed account (Company Details/Logo Upload/Profile Settings pattern) — avoids risking real, hard-to-reverse state (e.g. a saved payment method, a real subscription) on the one account every other spec file depends on.
- NOT a fresh disposable account registered per test (account-registration.spec.ts/forgot-password.spec.ts pattern) — would mean N redundant real email-verification round-trips per file for no benefit, since the state in question isn't shared across parallel browser projects the way the seed account's is.
- Instead: register **one** disposable account **once** in `test.beforeAll` (reusing `registerNewAccount()` / `completeProfile()` from `tests/utils/account.ts` and `getVerificationLink()` from `tests/utils/email.ts`), then run all of that file's scenarios serially against that one throwaway company (`mode: 'serial'`, chromium-only — same execution shape as the shared-account files, but touching only a disposable company instead of the real one).

Don't assume this generalizes without checking — re-verify per area. `tests/teams.spec.ts` confirmed this same third pattern works for Teams too (a fresh disposable account's default "My Team" and company-wide member list are fully isolated from every other account's). Integrations and Subscription (still ❌ as of this writing) should each get the same live-verification treatment before deciding which of the three patterns fits.

## Why `profile-settings.spec.ts`, `logo-upload.spec.ts`, and `company-details.spec.ts` run serial + chromium-only

Unlike the other spec files (which register a fresh disposable account per test), most of Profile Settings and all of Logo Upload and Company Details read/write the one shared seed account — Email and Username are read-only there, so there's no disposable-account escape hatch for most scenarios (and Logo Upload's and Company Details' tests are explicitly order-dependent on each other for the same reason). Running those tests across 3 parallel browser projects would race on that one account's state. So each of those files' main `describe` uses `test.describe.configure({ mode: 'serial' })` + `test.skip(browserName !== 'chromium', ...)`. Follow the same pattern for any new spec file that similarly can't avoid touching shared account state.

Company Details adds one more wrinkle worth knowing generally: if an area's fields are all client-side **required**, there is no way to ever restore that area back to a blank/unset state once any field holds a real value (required-field validation correctly blocks saving an empty value - this is normal behavior, not a bug to route around). Plan for this the same way Logo Upload already does for its logo: accept it as a permanent, harmless, clearly-labeled side effect in the Application Overview, don't try to force a "restore to blank" step that the UI genuinely can't support.

## Portability: multiple people/environments running this suite

This suite is designed to work against **any** seed account configured via `TEST_USERNAME`/`TEST_LOGIN_PASSWORD`, not hardcoded to the maintainer's specific account:

- `tests/profile-settings.spec.ts` does NOT hardcode expected First Name/Last Name/Phone values. `discoverSeedBaseline()` (called once via `test.beforeAll`) logs in and reads whatever those fields currently are, using that as the "restore point" for the rest of the file. If you add a new spec file that needs a known baseline for some shared-account field, follow this same discover-don't-hardcode pattern rather than writing literal expected values.
- `.github/workflows/playwright.yml` has a top-level `concurrency: { group: playwright-suite-seed-account, cancel-in-progress: false }` — this queues (never cancels) overlapping CI runs so two runs never mutate the shared CI seed account at the same time. `cancel-in-progress` is deliberately `false`: cancelling mid-run could skip a test's own restore-to-baseline cleanup step, corrupting the account for whichever run goes next.
- What this can't do: coordinate between two different **people** running locally at the same time against the same account. There's no code-level fix for that (no shared lock reaches across two separate machines). Each developer should register and use their own separate seed test account in their own `.env`, not share one set of credentials — see the README's "If you're a second person picking this up" note.

## Stripe restricted key for Test Clock investigations (and, as of 2026-08-28, general Stripe API cross-checks)

**Actively used by `tests/teams-plan-gating.spec.ts`, `tests/account-deletion-billing.spec.ts`, `tests/payments.spec.ts` test 6.5, and `tests/subscription.spec.ts` Suite 7** (live-verified end-to-end) - not just a speculative future capability. `teams-plan-gating.spec.ts`'s own `beforeAll` drives a real Stripe Test Clock directly via the REST API (plain `fetch()`, no `stripe` SDK dependency) to simulate real subscription time-passage: a normal disposable account never reaches a genuinely-lapsed-to-Free state on its own, since Stripe won't let a real billing period elapse in the time span of a test run. [Stripe Test Clocks](https://docs.stripe.com/billing/testing/test-clocks) solve this by simulating the passage of time on a real test-mode subscription, so the app receives the same webhook it would in production. See that file and `specs/teams-plan-gating-test-plan.md` for the full pattern (register → real Checkout purchase → real in-app cancellation → attach clock to the resulting customer → advance past `current_period_end` → poll for `ready` → confirm `status: "canceled"` before touching the UI at all).

**`tests/utils/stripe.ts`** holds the shared, reusable pieces of this pattern (`stripeRequest()`, `stripeFindCustomerByEmail()`, `stripeListCardPaymentMethods()`, `stripeFindSubscription()`) - extracted 2026-08-28 once a second consumer (`payments.spec.ts` test 6.5, see below) needed the same plain-`fetch()` Stripe REST pattern `account-deletion-billing.spec.ts` had already proven, so it wouldn't need its own third copy; `stripeFindSubscription()` was added the same day for a third consumer, `subscription.spec.ts` Suite 7 (see below). `account-deletion-billing.spec.ts` and `teams-plan-gating.spec.ts` still keep their own module-level copies of `stripeRequest()`/`stripeFindCustomerByEmail()` (deliberately not refactored to import the shared version - both were already live-verified and committed, and touching working, already-tested files for a pure DRY cleanup wasn't worth the risk). Any NEW file needing basic Stripe REST access should import from `tests/utils/stripe.ts` rather than adding a fourth copy.

**`payments.spec.ts` test 6.5** (closed a previously-documented "known verification gap" - see `specs/payments-test-plan.md` section 6.5 and finding 16): live-verified that resubmitting the exact same card as the currently-saved one never leaves a duplicate Stripe PaymentMethod behind, by querying `GET /v1/payment_methods?customer=<id>&type=card` before and after. The real mechanism is more interesting than "detects and skips" - Stripe creates a genuinely NEW PaymentMethod object on every single resubmission (different `id`, same `card.fingerprint`), and the app's backend cleanly detaches the previous one from the customer in the same save, so the count never grows. This required no new key permissions - `Customers: Read` already covers listing a customer's payment methods.

**`subscription.spec.ts` Suite 7** (native Cancel/Resume Subscription): previously asserted entirely on UI text/toasts for what happens to the real subscription. Now queries `GET /v1/subscriptions?customer=<id>` directly after test 7.3 ("Finish Cancellation") and after 7.6 ("Resume"), confirming `cancel_at_period_end` is genuinely `true` then `false` server-side. Unlike the payments.spec.ts 6.5 finding above, here the UI's claims matched Stripe's real state exactly in both directions - no surprise mechanism uncovered, just upgraded from "the UI says X" to "X is actually true".

- An **existing** customer (created through this app's own normal registration + Checkout flow) CAN be attached to a test clock after the fact - it does not need to be recreated from scratch via the API. Confirmed in Stripe's own docs.
- **"Automations" blocker: confirmed NOT an issue on this account (2026-08-27)** - Stripe's docs warn that an account with "Automations" configured (Dashboard → Billing → Automations, in test mode) can't attach an existing customer to a test clock. Live-verified via the API directly (not by reading the Dashboard UI, which turned out ambiguous - see below): created a real test clock attached to an existing customer, zero error. This path is confirmed usable.
- **A UI-only check of "Automations" is not reliable enough to trust on its own** - the Dashboard's "Automations" tab (the visual workflow-builder) showed empty, but the "Overview" tab of the same "Revenue recovery" section showed "Enable recovery emails"/"Use hosted recovery surface" already toggled on, and it wasn't clear from the UI alone whether those simpler toggles count as "Automations" for this specific restriction. Resolved the ambiguity by testing directly against the API (attempt to create a test clock for an existing customer; a real error message would name the blocker if there were one) rather than continuing to interpret Dashboard screenshots - more reliable and faster than guessing from the UI.
- If you need this, use a Stripe **restricted** key (`rk_test_...`), never the account's main secret key. Minimum scope actually needed for this kind of investigation: `Test Clocks: Write`, `Customers: Read`, `Subscriptions: Read`, `Invoices: Read` - everything else `None`. Least-privilege is deliberate here, not laziness: this key can reach a real (if test-mode) Stripe account, and a narrower key both limits blast radius if it ever leaked and keeps the list of "what could this have touched" short when debugging. Widen it later, on a concrete demonstrated need, rather than provisioning broadly up front - e.g. `Checkout Sessions: Read` was added mid-investigation specifically to diagnose a real CI-only Checkout bug (see the GPU/hCaptcha gotcha above), not requested speculatively in advance.
- **The key's actual value must live ONLY in `.env`**, as `STRIPE_TEST_RESTRICTED_KEY` - read it via `process.env.STRIPE_TEST_RESTRICTED_KEY` in code. Never write the real value into this file, `handoff.md`, a commit, or anywhere else that isn't `.env`/`.env.local` (both gitignored). `.env.example` has a placeholder showing the expected format.
- A restricted key already exists for the maintainer's own environment (name and permission scope recorded in `handoff.md`, not here, since that file stays local-only) - check there before creating a duplicate.

## Conventions for new spec files

- Locators: `page.locator('input[name="..."]')` for form fields, `page.getByRole(...)` for buttons/dialogs/roles, `page.locator('text=...')` for inline messages/toasts.
- One `test()` per test-plan scenario number, not one test per assertion — bundle related assertions with numbered-step comments matching the plan's steps.
- Tag any test that depends on the real pre-staging email pipeline (`/forgot-password` submission, reading a verification/reset email, etc.) with a trailing ` @real-email` in its title. **This includes every test in a file whose dependency is indirect via a shared `beforeAll`/`beforeEach`, not just the one test that literally reads the email** - e.g. every test in `tests/payments.spec.ts` is tagged, even though none of them read an email themselves, because the file's single `beforeAll` (registers one disposable account for the whole file, per the account-isolation pattern below) does. Live-verified this matters: leaving them untagged let a real-but-unrelated email-pipeline hiccup in that shared `beforeAll` fail CI's blocking "core" step for a reason that wasn't an actual regression - the exact failure mode this tag exists to route around.
- Every automated area starts as a live-verified plan in `specs/<area>-test-plan.md` (gitignored — contains real credentials in plain text, ask the maintainer for a copy or regenerate with the `playwright-test-planner` agent) before it becomes a spec file.
- When generating tests with the `playwright-test-generator` agent for a file that (like Profile Settings) touches shared account state, invoke it **sequentially per section, never in parallel** — parallel agent sessions would race on the same live account.
- After generating, actually run the tests against the real backend (`npx playwright test <file> --project=chromium`) before considering the work done — "it compiles" is not "it passes" in a suite with no mocks. Expect to find and fix real timing/race bugs, not just typos.
- Update the Portal Coverage Map in `README.md` when a new area's status changes.

## Known gotcha: running multiple `@real-email` spec files together locally can cause a burst of real-email timeouts that CI doesn't see

Live-verified 2026-08-24 while re-validating `account-registration.spec.ts`/`forgot-password.spec.ts`/`payments.spec.ts` together after the `email.ts` `since` fix (see the gotcha above): `playwright.config.ts` sets `fullyParallel: true` and `workers: process.env.CI ? 1 : undefined` — locally, `workers: undefined` lets Playwright auto-pick parallelism (4 on a typical dev machine), and `fullyParallel: true` means individual tests from *different* spec files can run concurrently, not just different files sequentially. Running several `@real-email`-heavy files together locally can therefore fire off several real account registrations within seconds of each other (e.g. `account-registration.spec.ts`'s test + both of `forgot-password.spec.ts`'s `@real-email` tests + `payments.spec.ts`'s `beforeAll` all racing at once). The real pre-staging backend's email-sending pipeline (Mandrill/SES) appears to queue/delay under that kind of simultaneous burst, consistently landing verification emails 1-5 minutes past the 150s/240s budgets — confirmed via direct IMAP checks each time: every "timed out" email had, in fact, already arrived, just late, never actually lost. **This is a *local-only* effect** — CI forces `workers: 1` specifically to avoid it, so a burst-flaky local run is not evidence CI will fail the same way (and empirically hasn't: a same-day CI run of the identical 3 files after this same investigation came back with only the usual scattered handful of independent `@real-email` timeouts, not a correlated pile-up). If a future session needs a clean local validation run of several real-email-heavy files at once (e.g. re-verifying a change to `email.ts` didn't regress anything), pass `--workers=1` to serialize them and avoid the burst entirely — accept it'll take longer wall-clock time in exchange for a result that isn't confounded by this effect.
